# 03 — UX specification

The web app (`packages/web`) is a local-first React SPA. Everything you can
see is a query over rows already in the browser; everything you can do is a
mutation from the shared vocabulary applied optimistically. The design goal is
that the tool feels like a native app with a keyboard, not a web form.

## 1. Information architecture

```
Firm
├── My work            assigned · created · watching · due soon · mentions   (GET /api/v1/my-work; local)
├── Inbox              notifications (synced, own rows)
├── Projects           one per desk / strategy / function
│   └── RATES
│       ├── Views      saved queries (list · board · timeline · dashboard), shared or private
│       │   └── /p/RATES/v/<viewId>
│       ├── Items      RATES-12 … (detail panel or full page)
│       ├── Activity   project feed (cursor over activity_events)
│       └── Settings   members · labels · default/allowed types
├── Search             deep search (server FTS + trigram) and palette (local)
└── Admin (firm admin) types · workflows · users · webhooks · integrations
```

Routes. `/p/:projectKey/v/:viewId` is the contract for views
(ARCHITECTURE.md §Web app). The rest of the route table is an implementation
detail; the recommended shape:

| Route | Screen |
|---|---|
| `/` | My work |
| `/inbox` | Notification inbox |
| `/projects` | Project list |
| `/p/:projectKey` | Redirect to the project's default view |
| `/p/:projectKey/v/:viewId` | View (list/board/timeline/dashboard) |
| `/i/:itemKey` | Item detail (full page); also opened as a side panel over any view |
| `/p/:projectKey/activity` | Project activity feed |
| `/p/:projectKey/settings` | Members, labels, types |
| `/admin/types`, `/admin/workflows`, `/admin/users`, `/admin/webhooks`, `/admin/integrations` | Admin |

Unsaved filter/sort/group edits on a view live in the URL query string until
"Save view", so a filtered URL is shareable without creating a view.

## 3. Command palette

Opened with `⌘K` (`Ctrl+K`), built on `cmdk`. One input, several modes
selected by what you type or by a prefix.

| Mode | Trigger | Behaviour |
|---|---|---|
| Navigate | default | Fuzzy over projects, views, items by key (`RATES-12`) or title (local `contains`/trigram-like scoring in memory); `Enter` opens |
| Create | `c` from any screen or `> create` | Title input; type picker (project default first); `⌘Enter` creates in the current project with `createItem` and opens it; typed fields can be filled in the detail panel |
| Action | `>` prefix, or when an item is focused/selected | Assign, set priority, transition (only transitions the engine says are allowed, others greyed with the failing guard), add/remove label, move to project, set due date, watch, copy link |
| Bulk | automatically when ≥ 2 rows are selected | Same actions applied as `bulkUpdateItems` / `bulkTransitionItems` / repeated `addLabel`; shows the count ("Assign 14 items to…") |
| Go to | `g` then a key (see keyboard map) | Direct jumps |
| Search | `/` or `? ` prefix | Deep search via `/api/v1/search` with snippets; local results shown instantly above, server results stream in |
| Help | `?` | Keyboard cheatsheet |

Palette results are ranked: exact key match, then items in the current
project, then recently opened, then everything else. Actions that need an
argument (assignee, label, project) open a second-level list in the same
palette; `Esc` goes back one level, not out.

## 5. Instant navigation guarantees

1. **No read waits on the network.** Projects, views, items, labels,
   workflows, types, relations, comments, watchers and notifications are in
   the local Replicache store (IndexedDB) and read through `useSubscribe`.
   Route changes render from local data synchronously.
2. **Writes are optimistic.** Every mutator applies the server's logic
   locally (`createItem` writes a `work_items/<id>` row with key `"<PROJECT>-?"`
   and `number = 0`; the pull replaces it with the server-assigned key).
   `transitionItem` runs the workflow engine locally so the card moves
   immediately.
3. **Rejections are visible, never silent.** If the server rejects a mutation,
   the next pull reverts the local row and an inbox row of kind
   `mutation_rejected` explains why.
4. **Poke → pull keeps tabs fresh** within about a second of any write by
   anyone; no manual refresh exists in the UI.
5. **Cold start** shows the app shell immediately and a progress indicator
   until the first full pull completes; a returning user starts from the
   persisted store and pulls the delta.
6. **Only two things go to the server for reads**: deep search and dashboard
   widgets that cover data outside the user's synced scope (rare, since the
   synced scope *is* the visible scope).

Offline: reads and writes keep working; the push queue drains on reconnect in
order (Replicache guarantees per-client ordering; the server enforces it).

## 6. Bulk edit flows

* Selection: `x` toggles, `Shift+click` ranges, `⌘A` selects everything the
  current filter shows (up to the mutation limit of 500 ids; beyond that the
  UI asks to narrow the filter).
* A selection bar appears above the view: count, "Assign", "Priority",
  "State", "Label", "Move", "Due", "Clear". Each opens the palette in bulk
  mode.
* `bulkUpdateItems` sends one patch for all ids in one transaction; the
  activity log records every item's changes under one `txn_id`, so the whole
  bulk edit is one undo unit and one webhook delivery per item.
* `bulkTransitionItems` evaluates guards per item and returns
  `{ok:[], failed:[{id, failures}]}`; the UI shows "12 moved, 2 skipped:
  RATES-4 (no assignee), RATES-9 (blocked by RATES-7)" with a link to each.
* Bulk from a board: dragging with a multi-selection moves all selected cards
  (same `bulkTransitionItems`).
* Board drag between columns where `column_field` is `state_id` chooses the
  transition whose `to_state_id` is the target column; if several exist, a
  small chooser appears; if none, the drop is refused with the reason.

## 7. Search behaviour

| Layer | Where | Latency | Scope |
|---|---|---|---|
| Palette / view filter `contains` | local | instant | key, title |
| Filter bar `search` field (`match` op) | local `contains` first; server FTS when the view is saved/shared and the local scan finds < N results (implementation detail) | instant → ~50 ms | key, title, description |
| Deep search (`/`) | `GET /api/v1/search?q=` | network | FTS5 over key/title/description, `bm25` rank + snippet; `LIKE` fallback on key/title for partial words; visibility-filtered |

Search syntax is SQLite FTS5: words are ANDed, `"exact phrase"`, `a OR b`,
`NOT word`, `prefix*`. Results show key, title, state chip, project, snippet.
Filter chips can be added from search results ("in RATES", "type bug") which
converts the search into a view spec you can save.

## 8. Notification inbox and low-noise principles

* The inbox is the only place notifications appear; there are no toasts for
  other people's actions. Badge count = unread rows.
* One row per (item, kind) stays unread and updates in place as more happens
  ("Alice and 2 others commented"); reading it clears all collapsed events.
* Rows carry actions: open item, mark read, and for `state_change` /
  `assigned` the allowed transitions as buttons (same engine check).
* Defaults are deliberately narrow (mention, assigned, reply, state change on
  your items, due soon). Watching an item is opt-in per item (`w`) and
  opt-out per item (`muted`), and "comments on watched items" / "state changes
  on watched items" are off by default.
* Preferences (`/settings/notifications`, implementation-detail route): per
  channel (in-app, email, Slack) a cadence (immediate / hourly / daily / off),
  the rule toggles, and quiet hours. Email and Slack digests render with
  `renderDigest`.
* `mutation_rejected` rows are always delivered in-app and auto-archive once
  read.

## 9. Item detail

Layout (panel or page):

1. **Header**: key (click to copy), type icon, title (inline edit `e`), state
   chip with transition buttons (allowed = enabled, blocked = disabled with the
   failing guard as tooltip: "needs an assignee", "blocked by RATES-9"),
   priority, assignee, due date, confidential toggle (editors; admins for
   others' items).
2. **Description**: markdown with `@[Name](user:<uuid>)` mentions rendered as
   chips; item keys auto-linked.
3. **Fields**: generated from the type's `field_defs` in definition order;
   kinds map to controls (select → combobox with option colours, user →
   people picker, date → date input, bool → switch, multi → chip input,
   `long_text` → markdown editor). Validation errors from `validateFields`
   inline.
4. **Relations**: parent breadcrumb (`item_ancestors`), children list with
   rollup bar (`done / total`, estimate done / total), "Blocked by" (open
   blockers highlighted), "Blocks", "Duplicates", "Related", external links
   (icon by `external_kind`, title from `external_ref.title`). "Add relation"
   opens the palette to pick an item or paste a URL (→ `links_to` external).
5. **Labels, watchers** (avatars; click to see reason), attachments.
6. **Comments**: threaded (`parent_id`), markdown, mentions, source badge
   (email / Slack / GitHub / MCP comments are marked), edit/delete own.
7. **Activity**: timeline grouped by `txn_id`; each group shows actor, source,
   time and the per-field diffs; "Undo" on the latest group you authored.

## 10. View toolbar and filter builder

Toolbar: view name (rename inline), kind switcher (list / board / timeline /
dashboard — switching keeps the `QuerySpec` and only changes presentation),
Filter, Sort, Group, Columns (list), Board options (column/swimlane field),
Timeline options (start/end/zoom/dependencies), "Save" / "Save as" / "Share"
(`is_shared`), "Set as default".

Filter builder:

* A row = field picker (built-ins by label from `BUILTIN_FIELDS`, then
  `fields.<key>` of the types present in the project with labels from
  `field_defs`, then `labels`, `parent_id`, `is_blocked`, `search`) + operator
  picker (filtered to what the field kind supports) + value control (macros
  offered for user/date fields: Me, Today, Start of week…).
* Groups: "All of" / "Any of" / "None of" nest `and` / `or` / `not`.
* The builder edits the `FilterExpr` JSON directly; a "JSON" tab shows and
  accepts the raw spec (validated with the zod `ViewSpec`).
* Changes apply instantly to the local result; the URL carries the unsaved
  spec; "Save" writes `updateView` (own or shared with `view.edit_shared`).

## 11. Admin editors

**Types** (`PUT /api/v1/types/:key`): name, plural, icon, colour, workflow,
container flag, active; field builder with key (locked once used), label,
kind, required, multi, options (value/label/colour), min/max, default,
show-in-list. Removing a field warns that existing values must be cleared
first (the DB trigger rejects unknown keys on the next write).

**Workflows** (`PUT /api/v1/workflows/:key`): state list (key, name, category,
colour, initial, order) and transition list (key, name, from = any/state, to,
guards, effects, order). Guard/effect editors are typed forms over the
`Guard`/`Effect` unions (field pickers, role pickers, category multi-select,
label names, templates, event kinds). A graph preview renders a state diagram.
`workflowEngine.validateDefinition` runs client-side before save and
server-side on save; errors are listed inline (no initial state, unreachable
state, unknown state reference, duplicate key).

Both editors write admin mutations (`upsertItemType`, `upsertWorkflow`) that
are logged like any other change.

## 13. Accessibility basics

* All interactive elements are real buttons/links with visible focus rings;
  the roving `j`/`k` focus uses `aria-activedescendant` on lists and boards.
* Palette is a `dialog` with `aria-modal`, labelled input, `listbox` results.
* Drag and drop has a keyboard path: `s` on a focused card opens the state
  chooser; timeline bars expose date inputs in the panel.
* Colour is never the only signal: state chips carry text, priority has an
  icon + label, option colours are decorative.
* Contrast ≥ 4.5:1 for text; dark mode follows the system preference.
* Reduced motion disables drag animations and pulse effects.
* Markdown content is rendered with semantic headings and lists; images have
  alt text from the attachment name.
* Every shortcut is listed in the `?` cheatsheet and reachable through the
  palette.
